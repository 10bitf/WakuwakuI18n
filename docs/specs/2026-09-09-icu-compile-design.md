# 复数与 ICU：构建期编译 —— 设计（2026-09-09）

> 起因在 Racing：做海外版时发现 i18next 的复数选择只认 `count` 这个魔法变量名，
> 而全仓的占位符叫 `{n}`；一条消息还只能有一个复数。用户裁定「改 wakuwaku-i18n，做到最好」。
>
> **这份文档不是实现，是把方案、契约变更、验收单钉住。** 动手前先过 spike（见 §7）。

---

## 1. 问题：三个，但只有一个是真的急

| # | 问题 | 严重度 |
|---|---|---|
| 1 | i18next 的复数选择**只认 `count`**，我们的占位符叫 `{n}` → 加复数那天，没传 `count` 的调用点**渲染成空白** | 🔴 静默 |
| 2 | **一条消息只能有一个复数**。Racing 有 9 条形如 `{races} 场 · {winners} 位分站冠军 · {drivers} 位车手` | 🔴 做不了 |
| 3 | 序数（英语 1st/2nd/3rd/**11th**）要另一套后缀 `_ordinal_*` | ◐ |

⚠️ **问题 1 最坏的部分是我们自己造的**：i18next 缺 `count` 时返回 key 本身（屏幕上一坨乱码，看得见），
而各消费方的 `parseMissingKeyHandler` 把它换成了空串（「缺 key 绝不把 key 显示给用户」）。
那条规矩本身对，副作用是**把库唯一的提示也吞了**。

> 记这一条不是为了追责，是因为它决定了修法：**我们吞掉了库的提示，就得自己补一个回来**
> （Racing 2026-09-08 已在取词层加了「占位符没填上」的开发期哨兵，那是止血不是治本）。

## 2. 《现成方案调研》

> 用户全局 CLAUDE.md 的造轮子闸门：i18n 属水电类，**没有这一节不许进实现**。

### 2.1 三条路

| 方案 | 代表 | 满足硬需求 | 体积 | 不用它的**具体**理由 |
|---|---|---|---|---|
| **A 运行时解析 ICU** | FormatJS / react-intl · `i18next-icu` | 🔴 **不满足** | polyfill **1.7 MB** | **依赖 `Intl.PluralRules`，而安卓微信基础库没有 `Intl`** —— Racing 的 `core/tz.js` 早有 plat-limit 记着这条（`dayjs-tz`/`luxon`/`date-fns-tz` 全因此不能用）。polyfill 装不下：Racing 主包只剩约 450 KB 余量 |
| **B 构建期编译** | **Lingui**（React 圈「性能党首选」）· `@messageformat/core` | ✅ 全满足 | **+7 KB** | ✅ **选它**（理由见 §3 实测） |
| C 各家自有复数 | i18next 的 `_one`/`_other` | ◐ 现状 | 0 | 就是问题 1/2/3 本身 |

### 2.2 那 MessageFormat 2.0（「最新标准」）呢

| | |
|---|---|
| 规范状态 | Unicode **Final Candidate（2025-03）**，spec-stable |
| 生产采用 | 🔴 **2026 年仍然罕见** |
| 进 JS 标准的门槛 | TC39 要**约十家公司在生产用过**才继续推进 —— **未达到** |
| 主流框架 | **一个都没设为默认**；FormatJS / react-intl 仍在 ICU 1 |
| 工具链 | 翻译平台与译员编辑器**还不认 MF2** |

**结论：MF2 是未来不是现在。** 现在上等于当小白鼠，且译员用不了。

✅ **但选 `@messageformat` 家族等于给 MF2 留门** —— MF2 的 JS 实现（`messageformat@4`）
就是同一批人维护的，将来迁移在同一个生态内。

### 2.3 一人日闸

不是自建，是接现成的编译器 + 一个 Vite/Astro 插件。**未超一人日**（估 0.5～1 人日 + spike）。

## 3. 实测数（2026-09-09 跑出来的，不是推的）

拿 Racing 的真实文案表（`miniapp/i18n/zh/`，926 条）跑 `@messageformat/core@3.4.0`：

| 问题 | 读数 |
|---|---|
| 现有 926 条是不是合法 ICU | 🎉 **926 / 926 是。一条都不用改** |
| 编译产物依赖 `Intl` 吗 | ✅ **不依赖**（118 字节/条纯函数，零 `Intl` 引用；en/de/ar 三个语种都验过）|
| 体积 | 33 KB → 40 KB（**×1.2**）。只编译**真的用到 ICU 特性**的那些则增量 ≈ 0 |
| 一条消息多个复数 | ✅ 实测 `{races, plural, ...} · {drivers, plural, ...}` → `1 races · 20 drivers` |
| 序数 | ✅ `selectordinal` |
| 中文表误写 `one` | ✅ **编译期直接报错**（`The plural case one is not valid in this locale`）—— 中文只有 `other` |

**关键推论：`{n} 站` 本身就是合法 ICU**（`{n}` 是简单参数）。所以：

- 中文表**一个字不用改**
- **魔法 `count` 名消失** —— ICU 把变量名写在消息里：`{n, plural, one{…} other{…}}`
- Racing 那 75 条 `{n}` → `{count}` 的迁移**直接作废，不用做了**

## 4. 🔴 这是身份变更，不只是 API 变更

README 第一句写着框架的自我定位：

> 「它**不提供取词**，取词交给 i18next」

本方案**正面改这一条**。改完之后框架管五件事，不是四件：

| | 现在 | 以后 |
|---|---|---|
| 禁裸中文 `lint-raw` | ✅ | ✅ 不动 |
| 一致性检查 `check` | ✅ | ◐ 小改（要认编译产物）|
| 豁免通道 `exempt` | ✅ | ✅ 不动 |
| 扫描 `scan` | ✅ | ✅ 不动 |
| **取词 / 格式化** | ❌ 交给 i18next | 🔴 **本框架提供**（编译产物 + 极薄运行时）|

**这一条必须显式裁定，不能顺手改掉** —— 它是框架 README 的第一句话。

## 6. 明确不改的

- `lint-raw` 的判据与豁免通道（`i18n-exempt-line`）
- `analyze` 的**占位符按出现次数比对**（2026-09-08 刚补了复数变体支持）
- `i18n.config.mjs` 的字段语义（`locales` / `scan` / `rawLint` / `assets`）
- **Wakuwaku 的批注 app**：它只把「元素 + 意见 + 源码位置」写进 `.annotations/pending.json`，
  **碰都不碰取词逻辑** —— 不受影响

## 7. 🔴 验收单：spike 要回答的三件事

按用户全局 CLAUDE.md 的实测闸，**写不出判读表就不许开工**。三件都只有跑一趟才知道。

| # | 问题 | 判读 |
|---|---|---|
| 1 | 编译步骤接得进 uni-app 的构建吗 | 接得进 → 继续；接不进 → 方案作废，回 §2 重选 |
| 2 | **小程序真机**跑得通吗 | 跑通 → 「无 `Intl`」这条硬约束解除；跑不通 → **看报错是不是 `Intl`**：是 → 编译没编干净；不是 → 另一个问题，别混为一谈 |
| 3 | 🔴 **改 JSON → 浏览器立刻变，这条不能坏** | 立刻变 → 过；要手动重启 → 不合格（现在 Wakuwaku 是重启 dev server，**新方案该更好不该更差**）|

⚠️ 第 3 条是用户 2026-09-09 追加的（「浏览器上直接改文字之类的」）。
**没有它，症状是「改了文字页面没反应，还以为改错了地方」** —— 那种问题最难查。

⚠️ 体积要**打出包来量**，不是拿 node_modules 的大小推算。

## 8. 风险与代价

1. **换的是运行时，不是加插件。** 虽然各消费方对 i18next 用得都很浅（只有取词 + 缺 key 兜底），但那是全站取词路径。
2. **4 个项目要一起验**，不是改完就完。Racing 是唯一的小程序（无 `Intl`），最该先验。
3. **多一个构建环节 = 多一个会坏的地方。** 编译失败要报得清楚，别变成「构建挂了但看不出为什么」。
4. **MF2 将来要再迁一次**（但那时全行业一起迁，且同生态内）。
5. ⚠️ **收益全在未来**：中文项目不需要复数（中文只有 `other`）。今天改完，界面一模一样。
   —— 所以它**不急**；急的是别在做外语版之前把方向定错，而方向现在定对了。
